# Правила работы с базой знаний Context-Kit

Закон базы. Его читает ИИ, который ведёт набор, первым при любом изменении.

Context-Kit — **агрегатор**: собирает практики ведения проектов с ИИ-агентами
из рабочих проектов, сверяет их между собой и с правилами набора. Ценность
базы — достоверность: запись, которой нельзя доверять, хуже пробела. Всё
ниже подчинено одному — отделять проверенное от предполагаемого.

## 1. Назначение и границы

Хранить: правила и приёмы, подтверждённые работой в проектах; грабли с
потерянным временем; шаблоны; пороги и их обоснование.

**Не хранить:**

* названия проектов, изделий, заказчиков, репозиториев, серверов, пути и
  учётные записи машин — набор готовится к публикации. Источник записи —
  **способ и метка проекта** (`P-01`), без названия;
* то, что есть в документации инструментов (Claude Code, Kimi Code, git) и
  легко ищется, — только ссылка и расхождение с реальностью;
* устройство `tools/*.py` — оно в docstring рядом с кодом;
* цифры о тарифах и квотах как факт: они меняются; такие записи — `не
  проверено` с датой.

Проверка на нужность: *«если не записать, сколько времени потеряет
следующая сессия или проект?»* Меньше десяти минут — не записывать.

## 2. Структура

```
knowledge/
  00_ПРАВИЛА.md      этот файл
  INDEX.md           id, утверждение, когда читать, по симптому
  10_ДОКУМЕНТЫ/      как устроены документы проекта: корневой файл, STATE, INDEX, журналы
  20_ПРИЁМЫ/         как работать с агентами и токенами
  30_ГРАБЛИ/         что ломается и почему; каждая запись — потерянное время
  40_СРЕДА/          установка набора, репозиторий, версии агентов
  50_ПРОЕКТЫ/        реестр подключённых проектов (обезличенный, метки P-nn)
```

Файлы нумеруются внутри раздела (`30-04_имя.md`), номер не переиспользуется.
Одна тема — один файл, не больше 200 строк (проверяет `check_docs.py`).

## 3. Шапка записи

```yaml
---
id: 30-04
title: Утверждение одной строкой, а не название темы
tags: [агенты, токены]
applies_to: Claude Code 2.x, Kimi Code
status: проверено | не проверено | устарело | действует
verified: 2026-10-19 — как именно подтверждено
source: практика P-01 | заметка | эксперимент (способ, без названий проектов)
---
```

`проверено` — воспроизведено или подтверждено в работе, с датой и способом;
`не проверено` — из чужого рассказа, документации, по аналогии;
`устарело` — было верно, перестало; хранится ради истории ошибки;
`действует` — только для самих правил (`00`) и записей раздела 50.
Записи без `verified` не имеют силы. `applies_to` называет агента и версию:
поведение агентов меняется. Разделы 30 и 20 при смене версии читаются как
`не проверено`, пока не подтверждены.

## 4. Как пользоваться

От дешёвого к дорогому: `skill/SKILL.md` (уже в контексте) → `INDEX.md`
(одна таблица) → файл записи (целиком, он короткий) → проект
(`tools/check_project.py <папка>`) → эксперимент, с записью результата.

## 5. Как добавлять запись

В момент, когда что-то сработало не так и причина найдена — не «потом».

1. Дубликата нет (INDEX, поиск по ключевым словам): дубликат хуже пробела.
2. Раздел, следующий свободный номер, файл по шаблону раздела 6.
3. **Обезличить** отдельным шагом: перечитать и убрать название проекта,
   репозитория, пути, имена людей. Пока пишешь, проект перед глазами.
4. Строка в `tools/when.txt`, `python tools/make_index.py` (пересобирает INDEX), строка в `CHANGELOG.md`.
5. `python tools/check_docs.py`, затем `git diff` глазами, коммит, push.
   Правило «один шаг — один коммит» действует и для набора.

Практика из проекта, не вошедшая в запись, не считается учтённой.

## 6. Шаблон записи

```markdown
# Заголовок
## Что происходит
Конкретно: симптом, цифры, команда.
## Почему
Причина; если неизвестна — так и написать.
## Как правильно
## Как неправильно      (обязательно в 30_ГРАБЛИ)
## Чем подтверждено
Что запускали, что получили; метка проекта и месяц.
```

## 7. Как обновлять и удалять

Обновление — правка файла, не новый файл: исправить, обновить `verified`,
при смене поведения старое утверждение уходит в раздел «История» с версией;
`title` в файле и в INDEX; строка в CHANGELOG. Запись `проверено`, которая
не сработала, понижается до `не проверено` сразу.

Не удаляют, а помечают `устарело`. Удалять можно только дубликат (оставив
ссылку) и заведомо неверную запись — со строкой в CHANGELOG. Номер не
переиспользуется.

## 8. Агрегация: как проект попадает в набор

1. Подключение проекта: `python tools/check_project.py "<папка>"` — отчёт
   «проект ↔ набор». Отчёт — в `local/` (в `.gitignore`), не в репозиторий.
2. Реестр: обезличенная запись `50_ПРОЕКТЫ/50-nn_P-nn.md` (метка, стек в
   общих словах, дата сверки, число ошибок/предупреждений, id записей,
   взятых из проекта). Соответствие метки и пути — в `local/projects.txt`.
3. Практики из проекта — записями 10/20/30 с `source: практика P-nn`.
   Расхождение между проектами — не усреднять: записать условия, при
   которых верно каждое.
4. Нарушение проектом правил набора — не повод править правило, а запись в
   отчёт; правило правится, только если нарушение системное (≥ 2 проектов).
5. Повторная сверка — раз в квартал и после смены версии агента.

## 9. Проверка целостности

Перед каждым коммитом: `python tools/check_docs.py` — шапки, INDEX ↔ файлы,
уникальность id, ссылки, размер записей, frontmatter `skill/SKILL.md`
(`description` ≤ 1024 знаков и в кавычках, если есть «: »), стоп-слова,
хук `commit-msg` (`core.hooksPath` = `tools/hooks`), автор коммитов клона.
`tools/stoplist.txt` и `local/` — **локальные**, не под git: названия
рабочих проектов вписываются в стоп-лист до первого коммита.
После `git pull --rebase` проверку прогнать заново: git сливает текст, а не
смысл.

## 10. Язык и стиль

Русский; имена команд, флагов, переменных — как есть. Числа с единицами:
«2 КБ», «100–200К токенов». Без «обычно» и «как правило» в `проверено`:
факт с условиями или `не проверено`. Примеры — рабочие целиком.
